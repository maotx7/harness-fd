# 汽车功能定义改写

当需要依据新项目需求改编已有功能定义 DOCX 时使用。本技能负责判断哪些内容应保留或变更；确定性工具可辅助抽取、校验和写入 DOCX。处理文件前阅读
[`../func-def-common/references/quality-delivery-contract.md`](../func-def-common/references/quality-delivery-contract.md)
中的共享契约。

## 使用场景

- 用户提供已有功能定义/模板，并要求调整逻辑、信号、术语、项目/控制器信息或章节结构。
- 没有可复用的原功能定义、需要根据 PRD 编写时，使用 `func-def-from-prd`；只有一句话想法时，使用 `func-def-from-idea`。

## 前置条件

- 确认原始 DOCX、目标需求来源、目标项目和信号矩阵，并核实各文件用途及矩阵版本。
- 如果某项决定会实质改变功能行为，且现有证据无法确定，使用 `func-def-clarify` 澄清，不要猜测。

## 执行流程

1. **盘点来源。** 抽取模板的功能层级和相关正文/表格，将目标需求拆成带稳定编号和来源位置的条目。对照原文抽查抽取结果。
2. **先建改写台账，再编辑。** 对每条重要模板内容和目标需求，标记为“保留、改写、新增、移除、待确认、不适用”之一，并记录来源证据、目标章节和理由。没有目标项依据的模板文字既不能默认有效，也不能默认错误；须依据证据判断，无法判断时标记待确认。
3. **核实项目事实。** 按信号语义与目标矩阵匹配。任何信号、报文、CAN ID 或取值的变更都保留精确矩阵证据，并区分已确认、歧义、缺失和冲突映射。
4. **形成完整的语义变更清单。** 覆盖行为、数值参数、触发/退出条件、HMI、异常/恢复逻辑、信号表、章节层级和项目术语，并在写入前检查跨章节影响。
5. **分批、可恢复地回填 DOCX。** 先保存台账和待执行操作。跨多个 Word run 定位正文并尽量保留样式；按标题路径限定范围；表格按表头和行内容定位，不使用固定单元格序号。分批写入新版本并记录检查点。仅对其明确支持的操作使用现有 `apply_signal_fixes.py`，不要自行编写 XML 修改。写入缓慢或失败时，应保留已完成审查并记录可恢复的回填阶段；不得丢失结果或让任务无响应。
6. **校验结果。** 重新打开最终 DOCX，在最终版本上重跑适用的信号和逻辑检查；逐项核对台账操作是否落入文档，确保未解决的阻塞项没有被伪装成已修复。条件允许时使用 `doc-review` 做独立语义复核，并依据来源核实其发现，不把脚本标记直接当成结论。
7. **交付。** 遵循共享质量与交付契约。最终 DOCX 必须送达当前前端会话或飞书；实质性改写建议附追溯报告，但报告不能替代 DOCX。

## 注意事项

- 章节匹配率不能证明语义正确。
- 不要全局替换可能在其他章节仍然正确的词句。
- 如果可以通过局部修改保留格式，不要把整段 Word runs 合并或清空重写。
- 只因 DOCX 回填或渠道发送需要重试时，不要重新做已完成的分析；从失败阶段恢复。

## 完成检查

- 每项重要需求都有处理结论和对应章节；未决项有明确原因。
- 每项项目级信号事实变更都能由目标矩阵佐证。
- DOCX 回填记录与最终文档内容和台账一致。
- 最终 DOCX 已持久化，并通过当前渠道实际送达。

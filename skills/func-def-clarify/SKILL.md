# 功能定义需求澄清

把简短、含糊或证据不足的需求逐步补成调用方可消费的功能定义输入包。问题与选项必须依据当前用户输入、附件、知识库命中和信号检索结果动态生成；不得维护固定业务问卷，也不得用常识替用户决定控制器归属、信号选择、优先级、故障策略或正式架构关系。对于一句话需求，由 `func-def-from-idea` 接续需求草案审批和功能定义生成；其他场景回到当前调用方。

完整数据契约见 [references/decision-protocol.md](references/decision-protocol.md)。生成或消费澄清请求前必须阅读该文件。

## 使用边界

- 当用户只有一句话需求、输入不足以支撑功能定义时使用。
- 当知识库、需求文件、模板或信号矩阵出现多个合理候选或相互冲突时使用。
- 当某个选择会改变功能正文、相关信号表、故障/恢复逻辑、架构图或校验结论时使用。
- 唯一证据可以自动确定、只是格式处理或不影响交付含义时，不要提问。
- 本技能形成决策输入，不生成 DOCX；完成后交回调用方继续对应场景的检索、校验、生成和交付。

## 核心流程

1. 汇总本轮可见的用户陈述、附件摘要、任务历史、知识库证据和信号检索结果，建立或更新需求画像。每个事实都记录值、状态和来源。
2. 先检索再提问。可以从已有证据唯一确定的事实直接标为 `retrieved` 或 `inferred`，不要让用户重复提供。
3. 计算生成缺口，只保留会改变交付物的决策点。按阻塞范围和下游影响排序，优先处理范围、责任控制器和核心行为，再处理接口、异常和交付状态。
4. 每轮提出一个决策主题；只有彼此独立且用户可以一次判断的项目才组成同一批。问题必须说明为什么需要人决定、引用了哪些证据以及各选项的下游影响。
5. 选项由当前上下文动态生成。存在合理推荐时可以给出推荐项和理由，但不得自动代替用户选择。始终允许用户选择“暂不确定”或补充自定义答案；未找到信号时必须提供待确认、信号申请或暂不纳入本版等保守路径。
6. 收到回答后用 `request_id` 和 `decision_key` 绑定原问题，更新需求画像与决策记录。不得把无关的普通聊天消息当作答案，也不得把旧请求的答案套到新问题。
7. 用更新后的画像再次检索和分析。若仍有阻塞正式版的人工决策，继续澄清；否则输出生成就绪摘要并交回发起澄清的场景技能：改写交给 `func-def-rewrite`，PRD 转写交给 `func-def-from-prd`，一句话需求交给 `func-def-from-idea`。不要自行切换场景或生成 DOCX。

## 人工决策判据

只有同时满足以下条件才向用户提问：

1. 当前证据不能唯一、可靠地确定结果；
2. 不同选择会实质改变功能边界、主要行为、控制器责任、信号/报文、优先级、异常策略、架构关系或交付状态；
3. 该决定属于产品、系统、功能或接口责任人，而不是排版和文档机械处理；
4. 可以把问题表达成可理解、有影响说明的选项，或者明确要求用户补充事实。

不得仅因某字段为空就提问。应先判断该字段是否适用于当前功能，并优先从知识库、项目绑定和信号目录恢复。

## 生成门槛

### 待确认草案

以下条件满足后可以建议生成草案：

- 功能目标和边界足以形成至少一个完整主流程；
- 项目/平台、责任控制器等无法确认的关键项已经被明确记录为待确认，而不是被猜测；
- 触发、主要行为和退出至少有可描述的当前结论；
- 所有未决项都有处置方式，并会进入 Word 批注和未决项清单。

### 正式版

只有影响正文、信号表、故障策略和正式架构关系的必需决策均已确认，关键引用已有来源，且下游场景技能定义的信号/逻辑校验达到交付门禁时才可建议生成正式版。交付门禁遵循 [共享质量与交付契约](../func-def-common/references/quality-delivery-contract.md)。

## 输出要求

- 使用协议中的结构化对象，不要只输出自然语言问句。
- `evidence` 只写实际读到的来源；没有证据时明确标为缺失。
- `recommended_option_id` 必须有证据或明确推理依据；否则为 `null`。
- 任何未决信号或架构连接都必须在下游以批注、虚线或待确认项呈现，不能伪装成已确认事实。
- 生成就绪摘要必须区分 `confirmed`、`retrieved`、`inferred`、`ambiguous`、`missing` 和 `pending`，并给出 `draft` 或 `formal` 建议。

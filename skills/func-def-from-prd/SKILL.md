# PRD 转汽车功能定义

当需求已有文档记录，但没有适合直接改写的原功能定义时使用。本技能由 Hermes 负责解释需求和设计功能逻辑；模板规定领域专属的结构和写法。处理文件前阅读
[`../func-def-common/references/quality-delivery-contract.md`](../func-def-common/references/quality-delivery-contract.md)
中的共享契约。

第一期目标是稳定 PRD 到高质量、可指导软件开发的功能定义 Word 的内容质量。先形成可审阅的语义功能定义，再使用独立排版生成 DOCX；不强制套用或回填既有项目模板。模板迁移属于后续阶段。

## 核心方法：章节职责，不是多 Agent

本技能中的“Agent”是章节编写职责和校验职责的名称，不代表必须启动多个智能体。Hermes 应在一个可恢复的工作流中，按章节顺序完成同一份 `function_definition_spec.json`：

```text
PRD事实表
  → 功能概述
  → 系统功能描述/场景
  → 系统需求
  → 功能架构/子功能
  → 接口和信号
  → 详细功能逻辑
  → 代码可实现性、追溯和验证校验
  → DOCX
```

每一章都是一次受约束的信息转换，不得把一章的内容凭空扩展成另一章的事实。章节之间通过稳定 ID 互相引用：`REQ`（需求）、`SC`（场景）、`FC`（子功能）、`SIG`（信号/接口）、`FL`（功能逻辑）、`TC`（验证用例）。

### 章节编写契约

每个章节生成前，必须明确四件事：本章目的、允许使用的输入、必须输出的字段、禁止做的事情。

| 章节 | 本章输入 | 本章必须回答 | 禁止事项 |
|---|---|---|---|
| 导言 | PRD元数据、项目和参考资料 | 适用范围、边界、来源、术语 | 不得引入未在来源中确认的车型事实 |
| 概述 | PRD目标、用户痛点、功能范围 | 功能做什么、为谁做、何时生效、输出什么 | 不展开未经确认的信号和算法参数 |
| 系统功能描述 | PRD流程、车辆状态、用户动作 | 用例、场景、系统边界和总体处理链 | 不把推断的接口写成正式信号 |
| 系统需求 | PRD条款、约束、异常和性能 | 可验收的`REQ`条目、来源、优先级、验证方法 | 不把“举一反三”的可选想法混入基线需求 |
| 功能架构 | 需求、场景、平台控制器证据 | 控制器职责、软件模块、时序、`FC`分解 | 不凭常识补控制器、总线或端点 |
| 接口和信号 | 架构、PRD接口、权威矩阵 | `SIG`接口契约、值域、方向、生产者/消费者、超时 | 不伪造正式信号名、CAN ID、报文或矩阵属性 |
| 具体功能逻辑 | 需求、场景、子功能、信号 | 可编码的`FL`条件/动作/状态/定时器/故障规则 | 不使用“适时处理、相关模块配合、按需”等模糊行为 |
| 校验和追溯 | 全部结构化模型 | 缺口、冲突、未决项、`REQ→SC→FC→SIG→FL→TC`闭环 | 不以正文关键词命中代替实际映射 |

### 软件可实现性标准

功能定义只有在每个行为都能转换为代码分支或状态机转移时才算完成。详细逻辑至少要写明：

```text
前置条件、使能条件、触发事件、输入信号、判断条件、执行动作、输出信号/事件、
状态变化、定时器或超时、互斥/优先级、重复触发抑制、异常处理、恢复条件、退出条件、部件。
```

推荐使用“当/若/则/否则/完成后/异常时”表达。对于识别、AI、HMI 等功能，还必须明确置信度或有效性判定、重试/抑制策略、输出保持时间和事件清除条件；无法从 PRD 或权威接口来源确定的值必须标记为 `TBD`、`pending` 或 `proposed`，并进入未决事项，不得暗中猜测。

### 需求扩展边界

需求挖掘只能产生三类结果：

- `confirmed`：PRD或用户明确要求，必须进入基线；
- `derived`：为实现已确认需求不可缺少的派生约束，必须说明推导依据；
- `optional`：可选增强或后续版本建议，必须单独列出，不能伪装成基线需求。

“举一反三”不等于擅自扩大功能范围。未确认的控制器、信号、阈值、算法能力和用户承诺都必须保留为待确认事项。

## 使用场景

- 用户提供 PRD、需求文档或结构化需求，并要求生成汽车功能定义 DOCX。
- 如果用户主要提供已有功能定义并要求改编，使用 `func-def-rewrite`；如果从一句话想法开始，使用 `func-def-from-idea`。

## 前置条件

- 确认目标项目、功能领域、需求来源、信号来源、交付渠道及用户指定的参考资料。信号来源可以是目标项目已发布的信号库，也可以是用户为本任务提供/指定的信号矩阵。
- 只能选择与功能领域匹配的已注册模板或用户指定模板。不得用其他领域的模板替代。如果没有适用模板，先提供明确标注的草案计划，并请求用户补充模板或确认领域。

## 执行流程

1. **先建立 PRD 事实表和语义工作包。** 记录来源位置、原文事实、范围、冲突、缺失行为、推导项和待确认项；产出 `function_definition_spec.json`，至少包含 `requirements`、`subfunctions`、`scenarios`、`chapters`、`signals`、`logic`、`traceability` 和 `validation_cases`。不要让最终正文成为需求分析的唯一工作记忆。
2. **按章节职责顺序生成，不跳章。** 先完成导言和概述，再完成系统功能描述/场景，然后形成系统需求，之后形成架构和子功能，再查信号，最后写详细逻辑。每章完成后检查它是否只使用了允许输入，并把输出 ID 写回工作包。
3. **固定章节结构。** 最终草稿必须包含：导言、概述、系统功能描述、系统需求、接口和信号、具体功能定义、需求和信号追溯。系统功能描述中必须有主功能、功能场景、系统功能架构、子功能分解、系统功能描述、系统边界和网络拓扑；具体功能定义中必须有子功能概述、逻辑架构、场景和时序、信号交互、变量/参数、详细功能描述、故障处理、恢复、安全和性能。
4. **建立可追溯的需求清单。** 将需求拆分为带稳定编号和来源位置的条目，标记 `confirmed/derived/optional/pending/conflict`、缺失行为、范围、约束和验收条件。每条基线需求必须映射到至少一个子功能、场景、逻辑和验证用例；不能映射的需求阻止正式版输出。
5. **先建场景和状态模型，再写正文。** 每个子功能至少关联需求、场景、信号和逻辑。每个场景必须具备目的、前置条件、使能条件、触发条件、执行步骤、输出、完成条件、退出条件、异常处理和恢复条件，形成“条件→触发→执行→结果→退出/异常”的闭环。对有并发、超时、去抖或重复触发风险的功能，同时建立状态和转移规则。
6. **先查信号，再决定复用或新增。**
   - 先确定本任务唯一的信号依据：用户明确指定了矩阵时，直接检索该矩阵并记录文件、工作表和版本/日期；否则查询目标项目已发布的信号库，并固定本任务使用的矩阵版本。若两种来源都提供且内容/版本冲突，先澄清采用哪一个，不要混合映射。
   - 写正文前，按功能语义、目标控制器和发送/接收方向查询信号。找到语义和接口均匹配且证据充分的信号时，直接复用其正式名称及报文、CAN ID、方向、取值/枚举等已定义属性，并记录来源。若结果为候选/需复核（如 `REVIEW`），先核对端点和值定义；无法判定时先澄清，不要因为自动检索未确认就新增重复信号。
   - 只有在所选信号依据中确认不存在可复用项后，才为功能定义新增“信号需求”条目，说明建议名称/语义、用途、方向、生产者/消费者，以及证据能够支持的数据类型、单位、范围、周期等。命名建议遵循项目规范；规范未知时标为建议名。无法确定的字段标为“待定义/待分配”，并明确该项是新建提案、尚未进入正式信号库；不得伪造正式信号名、报文、CAN ID 或接口属性。
   - 新增信号需求应进入交付文档和追溯清单；需要正式写入信号库或修改用户矩阵时，只有在用户明确要求且当前工具支持该操作时才执行，否则将其作为待申请/待分配项交付。
   - 如果项目库和用户提供的矩阵都不可用，不能据此断言“没有该信号”。如需求要求该接口，可在草案中列出待核实/拟新增的信号需求，并标记需要用目标矩阵复核；不得把它写成已确认的新建信号。
7. **按固定章节生成连贯正文。** 先由行为模型生成章节内容，再做工程化行文审查。每句话应明确对象、条件、动作和结果；统一术语；使用“当/若/则/否则/完成后/异常时”等连接逻辑；禁止用“相关模块配合、适时处理、正常情况下、按需处理”等模糊表达替代行为定义。润色不得改变条件、时序、阈值、信号含义或故障策略。
8. **进行详细逻辑可实现性审查。** 对每个 `FL` 检查是否存在输入、可判定条件、输出、状态初始化、退出条件、无效值处理、超时/重试、重复触发抑制、并发优先级、故障降级和恢复规则；从 `FL` 生成或补齐 `TC`，确保软件和测试人员可以直接使用。
9. **执行语义质量门禁。** 使用 `skills/func-def-gen/scripts/prd_quality_verify.py` 校验章节完整性、需求覆盖、子功能/场景/信号/逻辑/验证双向追溯、场景闭环、状态完整性、占位内容和模糊行文。草稿可保留明确标记的 `warning`，但 `error` 不得通过；正式版还必须消除会阻塞实现的未决信号、未定义阈值和模糊表达。
10. **生成独立排版 DOCX（第一期）。** 语义草稿通过质量门禁后，使用 `skills/func-def-gen/scripts/render_prd_spec_docx.py` 生成独立排版 Word。文档必须包含固定章节、场景闭环、信号表和需求/信号追溯；不得读取或强制回填项目模板。所有正文标题必须显式带层级编号，且与目录一致：一级章节使用 `3`，二级小节使用 `3.1`，场景/子流程使用父小节编号继续下钻（例如 `6.3.1`）；编号不得只依赖 Word 的自动编号。生成脚本只能读取已校验的 `function_definition_spec.json`。
11. **模板回填（后续阶段，可选）。** 只有用户明确要求迁移到指定项目模板时，才进入模板回填。DOCX 编辑前先持久化行为模型和写入计划；保留模板结构与 Word 格式，并按标题路径和表头定位写入。
12. **交付第一期产物。** 至少交付独立排版的最终 DOCX、`function_definition_spec.json`、功能定义正文、`quality_report.md`、需求追溯、信号追溯、逻辑校验和验证用例。质量报告存在阻断问题时不得交付或标记完成。

## 注意事项

- 相似功能定义可以参考写法，但不能替代 PRD。
- 章节结构完整不代表需求逻辑正确。
- 不要将一个领域的术语、故障章节或信号表布局强加给其他领域。
- 仅生成本地文件不能视为任务完成。
- PDF/模板只能提供章节结构、写法和内容粒度参考，不能直接替代当前 PRD，也不能把其中的业务事实复制到新功能。
- “无信号矩阵”不等于“无信号需求”。涉及接口的场景仍必须写语义信号、建议名称、方向、生产者、消费者、用途和 `proposed/pending` 状态。
- 必须章节不能用空白、`TBD` 或 `NA` 伪装完成；确实不适用时要说明理由并保留追溯。
- 参考平台功能定义时，吸收其控制器职责、接口契约、状态/初始值、车型分支、故障检测、恢复和详细条件逻辑的写法；只能借鉴结构和粒度，不能复制其业务事实或信号。
- “Agent”只表示章节职责和审查职责；除非运行时另有明确编排，不得为了满足本技能而伪造多 Agent 协作或把章节遗漏归因于 Agent 未调度。

## 完成检查

- 已记录所选模板和领域，功能内容符合模板实际结构。
- 每条需求都有可追溯状态和去向；每个信号均有明确结果：复用且可回源、新增且标注为待定义/待分配，或因来源冲突/证据不足而待确认。
- 每条基线需求均能沿 `REQ→SC→FC→SIG→FL→TC` 追溯；每条详细逻辑均能反向追溯到需求和场景，并具备可判定输入、输出、状态和故障行为。
- 最终 DOCX 可正常打开、通过适用校验，并通过当前渠道送达。

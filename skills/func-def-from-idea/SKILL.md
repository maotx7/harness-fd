# 一句话需求到汽车功能定义

当用户只提供简短或不完整的汽车功能想法，需要经过多轮澄清、审批需求草案后才能形成汽车功能定义 DOCX 时使用。这是一个分阶段的持久化任务，不应试图在一条聊天回复中完成。开始前阅读
[`../func-def-common/references/quality-delivery-contract.md`](../func-def-common/references/quality-delivery-contract.md)
中的共享契约。

## 使用场景

- 用户只给了一句话或几条简短描述，行为细节不足以支撑可靠的功能定义。
- 已有完整 PRD 时使用 `func-def-from-prd`；已有适合改编的功能定义时使用 `func-def-rewrite`。

## 前置条件

- 将原始需求、上传材料、选定项目/领域、矩阵、决策和产物绑定到稳定的 `task_id`。始终恢复同一任务；不能仅因打开了新会话就创建重复任务。
- 使用任务 API/运行时实际支持的阶段和状态名称。先读取任务快照，不要自行发明技能专用阶段，也不要在未核实的情况下认定状态迁移已成功。
- 无人值守恢复需要持久化任务协调器。仅靠技能无法恢复进程退出后只存在于 Agent 内存中的运行状态。

## 执行流程

1. **预检并绑定任务。** 确认项目/领域、可用模板、需求材料、矩阵和交付渠道。开始长任务前持久化输入产物编号/版本和检查点。若已有任务，先读取快照并从该任务恢复。
2. **基于证据澄清。** 调用 `func-def-clarify`。提问前先检索可用的项目、知识库和信号证据。只询问会实质改变范围、行为、控制器责任、信号、HMI、故障/恢复策略或架构关系的决策。每个问题须先持久化再展示；等待用户时将任务标记为 `waiting_user`，不要让生成请求或 HTTP 请求一直挂起。
3. **形成需求草案。** 输出结构化行为方案，包含范围、主流程、触发/守卫条件、输出/HMI、退出条件、异常/恢复、信号语义、假设和未决项。每项决策都注明证据来源和状态。请求用户审批前，先持久化草案和决策记录。
4. **等待审批。** 用户批准后，在同一任务中继续调用 `func-def-from-prd`，并沿用已批准的需求产物、矩阵绑定、决策和 `task_id`。收到修改意见时只修订受影响的需求项，不要求用户重新上传已有材料。
5. **生成并校验 DOCX。** 按 PRD 技能中的领域模板、行为模型、信号核实和 Word 回填流程执行。确保 `idea_to_spec` 任务与直接 PRD 任务一样必须通过 DOCX 交付门禁；不能因为场景不同而跳过文档校验。
6. **保存检查点并恢复。** 通知用户前，持久化每个已完成阶段的产物和待办事项。若进程或工具调用失败，只从最近的未完成阶段恢复。如果任务处于过期的 `running` 状态，不要悄悄创建重复任务，也不要声称它仍在运行；先检查日志/快照并使用运行时支持的恢复迁移。若没有恢复方式，保留已有产物并说明具体阻塞原因。
7. **完成交付后再结单。** 将最终 DOCX 持久化为输出产物，通过当前前端会话或飞书渠道发送，并确认渠道返回结果。可附追溯/澄清报告，但不能用报告替代 DOCX。只有交付成功后才能标记为 `completed`；发送失败时保留产物，仅重试发送，不重复执行已完成的分析或 DOCX 生成。

## 注意事项

- 不要为了减少一轮沟通，就把缺失事实写成确定结论。
- 不要把 `waiting_user` 当作失败，也不要把 WebSocket 断开当作任务完成。
- 除非运行时确实支持恢复，否则不要假设持久化状态一定可恢复；尤其要核实过期 `running` 任务的处理方式。
- 只生成了中间 PRD 不代表任务完成。最终 DOCX 必须送达用户当前使用的渠道。

## 完成检查

- 已批准的需求草案和决策均已持久化，并关联到同一个任务编号。
- 恢复后从最近检查点继续，既不丢失之前的输入，也不重复执行已完成阶段。
- 最终 DOCX 已校验、可作为产物重新获取，并在任务结单前通过前端或飞书机器人送达。

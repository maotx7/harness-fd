# 功能定义文档复核

本技能对照本次任务的需求来源、目标模板和信号矩阵，找出最终 DOCX 中有证据的问题。Hermes 负责理解需求、判断功能行为和评估问题；脚本只在能减少机械错误时用于抽取、比对、汇总或添加批注。

## 何时使用

- 对已生成的功能定义做独立质量复核，尤其在正式交付前。
- 排查需求遗漏、逻辑矛盾、信号事实错误、跨章节不一致或模板章节误用。
- 不用于替用户决定有歧义的产品/系统策略，也不自动重写业务逻辑。

## 输入与证据优先级

使用当前任务中可用的最终 DOCX、需求来源、实际采用的模板/领域规范、目标项目矩阵和已确认决策。缺少某类来源时明确标记检查范围受限，不用相似历史文档补造目标项目事实。

证据优先级：用户明确确认的决策和当前需求源决定预期行为；目标项目矩阵决定信号、报文、CAN ID、周期及枚举事实；选定模板决定章节结构和领域写法；历史文档只能提供参考模式。

## 复核流程

1. **确认材料身份。** 记录需求、DOCX、模板、矩阵的文件/版本；识别最终输出版本，确认抽取内容与原文大体一致。PDF、复杂表格或 Word 文本抽取不完整时，回看原文件相关页/段/单元格。
2. **建立双向追溯。** 按稳定 ID 梳理材料中的功能要求，并映射到 DOCX 章节。另从 DOCX 抽取每项实质行为，反查需求、已确认决策或项目证据；把无依据的行为作为推断/待确认，而不是默认正确。
3. **做语义复核。** 对每个功能检查触发/前置条件、状态与执行顺序、输出、退出、互斥/优先级、HMI、异常/超时/降级/恢复及跨章节关联。判断“需求→功能定义”是否保留了原意，而不只是关键词或信号名命中。
4. **做领域和信号复核。** 检查章节是否放在所选领域模板的正确位置、该领域规定的内容是否遗漏；每个信号事实须能回到目标矩阵及版本。区分缺失、歧义、冲突和明确错误，不把相似项目的信号映射当作证据。
5. **按严重性登记发现。** 每条发现包含 ID、严重性、章节/定位、相关需求 ID、实际证据、影响和建议动作。没有证据或无法确认的内容标为待核实，不写成确定缺陷。区分阻塞交付的问题和非阻塞建议。
6. **用工具辅助而不服从工具。** 可用 `scripts/` 做文档/需求抽取、精确匹配、跨表一致性检查、问题合并或批注。抽样核对抽取结果；审阅其误报和漏报。脚本没有报告问题不等于逻辑正确，脚本报告问题也不等于业务上确有错误。工具不可用时，可由 Hermes 直接完成有来源的语义复核，不因 Python 依赖缺失中断。
7. **输出审查结果。** 生成简明复核报告和可追溯问题清单。只有已由证据确认且机械替换不会改变业务语义的问题才可建议自动修正；有歧义的逻辑问题交 `func-def-clarify` 或责任人裁决。不要未经授权直接覆盖原 DOCX。

## 输出

按任务需要生成以下产物；中间 JSON、日志和报告用于追溯，可选，不得取代调用方要求的最终功能定义 DOCX：

- 需求与文档章节映射/覆盖状态；
- 带证据、定位和严重性的审查问题清单；
- 需要时生成带批注的审阅副本和 Markdown 报告。

最终交付仍由调用方场景技能负责。若审查属于 rewrite、PRD 转写或一句话需求工作流，遵守其共享质量与交付契约：最终 DOCX 必须持久化并回到前端或飞书；不能因为可选复核附件未生成而阻塞 DOCX 交付。

## 问题状态建议

- `confirmed_issue`：来源直接证明最终文档存在错误或遗漏；
- `needs_decision`：多个合理解释会改变功能行为，需由责任人决定；
- `unverified`：当前材料不足以确认正确性；
- `suggestion`：改进建议，不构成交付阻塞；
- `not_applicable`：该检查项不适用于当前功能或领域，记录原因。

不得仅凭自动匹配率或固定阈值判定文档合格。交付结论应说明检查覆盖范围、未解决阻塞项和工具局限。

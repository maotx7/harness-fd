# 功能定义质量与交付契约

`func-def-rewrite`、`func-def-from-prd` 和 `func-def-from-idea` 共用本契约。各场景技能负责领域分析；本契约规定共通的证据、产物和交付要求。

## 证据与不确定性

- 用户明确作出的决定和当前需求来源是预期行为的依据；目标项目的信号矩阵是信号、报文、CAN ID、周期和取值事实的依据。
- 模板或知识库检索结果只能作为参考，不能证明其中的项目专属行为适用于当前项目。
- 对每项重要需求或改写内容，保留来源位置和目标章节，并标记为 `confirmed`、`inferred`、`pending`、`conflict` 或 `not_applicable`。不得把推断悄悄写成事实。
- 草案和正式版必须区分。草案可以包含明确展示的待确认事项；正式交付不得隐藏仍未解决且会阻塞行为定义的问题。

## PRD 语义草稿章节契约

第一期 PRD 到功能定义必须先形成语义草稿，再生成独立排版的 Word。该阶段不强制依赖或回填项目模板；模板回填只在用户明确要求迁移时执行。语义草稿固定包含以下章节：

1. 导言；
2. 概述；
3. 系统功能描述（主功能、功能场景、系统功能架构、子功能分解、系统功能描述、系统边界和网络拓扑）；
4. 系统需求（功能、车辆及环境、诊断和故障、功能安全、性能）；
5. 接口和信号（HMI、电子接口、信号接口、信号定义和状态）；
6. 具体功能定义（子功能概述、逻辑架构、场景和时序、信号交互、变量/参数、详细功能描述、故障定义和处理、故障恢复、功能安全、性能规范）；
7. 需求和信号追溯。

每个子功能必须关联需求、场景、信号和详细逻辑。每个场景必须写明目的、前置条件、使能条件、触发条件、执行步骤、输出、完成条件、退出条件、异常处理和恢复条件。场景必须形成闭环，不能只写功能目标或操作步骤。每条可执行行为还必须能沿 `REQ→SC→FC→SIG→FL→TC` 追溯到验证用例。

Word 正文标题必须显式携带层级编号，并与目录保持一致：一级章节使用 `3`，二级小节使用 `3.1`，场景和子流程使用父小节编号继续下钻（例如 `6.3.1`）。编号直接写入标题文本，不能只依赖 Word 的自动编号功能；章节和小节应按固定契约顺序编号，避免模型输出字段顺序变化导致目录漂移。

正文必须保持工程化行文：同一对象和信号统一命名；每个行为说明对象、条件、动作和结果；复杂流程按步骤拆分；不得用“相关模块配合”“适时处理”“正常情况下”“按需处理”等模糊表达替代具体逻辑。行文润色不得改变结构化行为模型。

## 章节职责和可实现逻辑

“Agent”在功能定义任务中仅表示章节编写/审查职责，不要求真实多智能体调度。PRD 到功能定义按以下顺序完成：

```text
PRD事实表 → 概述 → 场景 → 需求 → 架构/子功能 → 接口/信号 → 详细逻辑 → 校验/验证
```

各章节只能使用其规定的上游信息，不得将未经确认的推断写成接口或产品承诺。详细逻辑必须至少包含前置条件、使能条件、触发事件、输入、判断、动作、输出、状态变化、定时器/超时、去重或优先级、异常、恢复和退出条件。识别、AI、HMI 等功能还必须定义有效性/置信度、重试或抑制、输出保持和事件清除规则；缺失信息必须显式标记为 `TBD`、`pending` 或 `proposed`。

参考成熟平台功能定义时，应吸收控制器职责、接口契约、初始值、状态机、车型/配置分支、故障检测、恢复和性能验证的写法，但不得复制参考文档的业务事实、信号或车型结论。

## 信号最低要求

- 有信号矩阵时，正式信号必须可回溯到矩阵，并核对报文、CAN ID、方向、生产者、消费者、周期、数据类型、范围和枚举值。
- 没有信号矩阵时，接口相关场景仍必须有信号需求，至少写语义名称、建议名称、方向、生产者、消费者、用途和 `proposed/pending` 状态；不得伪造正式名称、报文或 CAN ID。
- 5 章信号接口、6 章信号交互和场景正文必须双向引用同一信号语义；信号表中未被正文使用的信号属于质量问题。

## Word 回填

- 将语义决策与 DOCX 写入分开。应用修改前先持久化已审批的变更台账。
- Word 正文可能分散在多个文本片段（run）中。应跨片段定位目标文本，只修改预期内容，并尽可能保留段落和样式格式。
- 按标题路径限定修改范围；表格按表头和行内容定位，不假设合并单元格表格使用固定序号。
- 分批写入新版本。每批完成后记录已完成的操作编号和下一个待处理操作。发布前校验 DOCX 包，并将实际改动与台账逐项核对。
- 回填失败时保留分析结果和待执行台账。从回填阶段继续；不得重启需求分析，也不得谎称回填成功。

## 产物与交付

- 最终功能定义 DOCX 是必需交付物。报告、本地路径或“文件已生成”的文字不能替代文档本身。
- PRD 新建功能定义默认使用独立排版 DOCX。独立排版文档必须由已通过语义质量门禁的 `function_definition_spec.json` 生成，不得用空模板、占位章节或模板回填结果替代正文质量。
- **固定生成目录。** 通过 Hermes/前端任务执行时，唯一正式目录为运行时提供的 `HERMES_TASK_OUTPUT_DIR`（由持久化 `task_id` 派生）。生成脚本的 `out`、最终 DOCX 和适用的 `quality_report.md` 或 audit/signals/logic 报告都必须直接写入该目录；禁止把正式产物写到项目根目录、共享 `runtime/outputs`、其他任务目录或临时目录。不要为“方便回传”再复制一份。
- **固定回传对象。** 一个任务只交付该目录中本次生成、校验通过的唯一最终 DOCX。缺少 DOCX、存在多个本次 DOCX、校验报告不在该目录或校验不通过时，应停止并报告具体阶段；不能扫描其他目录、挑“最新文件”或拿旧文件兜底。前端/飞书的产物链接由应用持久化并返回，技能回复无需构造本地路径或 MEDIA 标记。
- 将最终 DOCX 持久化为输出产物，并通过当前用户渠道发送/附加：前端聊天窗口或飞书机器人。飞书优先发送可直接获取的文件；无法直接发送文件时，提供有效下载链接。没有成功的渠道返回结果，不得声称已经送达。
- 区分 `generated`（已生成）、`persisted`（已持久化）和 `delivered`（已送达）。只有最终 DOCX 可重新获取且渠道送达成功后，才能将任务标记为 `completed`。渠道失败时保留产物并进入可重试的送达状态；不要为了重试发送而重新生成已完成的内容。
- 中间追溯产物很有价值，但并非全部必交。存在实质改写、未决事项、信号映射或长时间任务时，建议生成简明追溯报告，将需求编号/来源位置关联到决策和最终章节。其他产物（需求清单、改写台账、信号映射、校验报告）仅在有助于审阅或恢复任务时保留。不得让可选产物阻塞最终 DOCX 送达。
- 在任务记录中保存产物编号、版本、任务编号和送达状态。即使客户端断开，用户也应能从任务/产物历史中重新获取同一份输出。

## 结单前检查

标记为 `completed` 前，逐项确认：

1. 最终 DOCX 存在、可正常打开，且已通过适用的信号、逻辑和结构检查；未决事项已披露。
2. DOCX 已保存为可重新获取的输出产物，而不是只留在临时工作区。
3. 当前渠道已收到 DOCX 文件或可用的下载附件/链接。
4. 任务快照和面向用户的完成消息都指明实际送达的文档；可选追溯材料明确标为辅助材料。

任何一项未通过时，说明当前卡在 `backfill`（回填）、`validation`（校验）、`persistence`（持久化）或 `delivery`（送达）中的哪一阶段，并保留足以继续处理的状态。
